# Аудит безопасности и надёжности

Дата: 2026-08-29  
Область: проект `C:\Programming\trading` (проверка без внесения изменений в код).

## Итог

В текущем состоянии сервер нельзя безопасно публиковать в интернете: HTTP API может совершать реальные торговые операции без проверки личности пользователя. До исправления критических пунктов ограничить сервер локальной сетью или отключить торговые маршруты.

## Критические проблемы

### 1. Нет аутентификации на торговых API

Маршруты создания/отмены ордеров и рыночной продажи не требуют входа, API-токена или сессии. Любой, кто имеет сетевой доступ к серверу, может вызвать их от имени владельца Coinbase-ключей.

Примеры:

- `server.js:223` — `POST /api/market-sell`
- `server.js:270` — `POST /create-sell-order`
- `server.js:346` — `POST /cancel-order`
- `server.js:538` — `POST /create-market-buy-order`
- `server.js:582` — `POST /create-buy-order`

Исправление:

1. Добавить обязательную аутентификацию для всех API, особенно изменяющих состояние.
2. Использовать защищённую серверную сессию в cookie (`HttpOnly`, `Secure`, `SameSite`) либо надёжный bearer-token, хранимый только на сервере.
3. Перед созданием ордера добавить подтверждение/лимиты: разрешённые пары, максимальную сумму, rate limit, журнал аудита.

### 2. CORS разрешён любому сайту

В `server.js:92` сервер выставляет `Access-Control-Allow-Origin: *`. Вместе с отсутствием аутентификации сторонний сайт может посылать торговые запросы в API пользователя.

Исправление:

- Удалить самописный CORS middleware, если фронтенд раздаётся тем же origin.
- Иначе задать строгий список разрешённых доменов и методов; не использовать `*` для торговых API.

### 3. Секрет Telegram выдаётся через API

`GET /get-settings` в `server.js:112` возвращает объект настроек полностью, включая Telegram Bot Token. `POST /save-settings` в `server.js:118` принимает и сохраняет этот токен.

Исправление:

- Хранить Telegram token и chat ID в переменных окружения/secret manager, не в `settings.json`.
- Никогда не включать token в HTTP-ответ.
- Для UI возвращать только флаг `telegramConfigured: true/false`.

### 4. Секреты обнаружены в файлах проекта

Обнаружены встроенные ключи внешних сервисов и файл service account Firebase. Значения намеренно не записаны в этот отчёт.

Затронутые места:

- `server.js:42` — ключ внешнего API задан прямо в коде.
- `src/reversal/run-scan.js:7` и `src/reversal/diagnose.js:10` — запасной ключ в коде.
- `cb/serviceAccountKey.json` — закрытый ключ service account.
- `cb/tokenTimeReal.js:110` — ключ внешнего API в исходнике.

Исправление (срочно):

1. Отозвать/перевыпустить все перечисленные ключи: их следует считать скомпрометированными.
2. Удалить значения из файлов и истории Git, если они когда-либо попадали в коммиты.
3. Использовать только переменные окружения или секрет-хранилище.
4. Добавить проверку секретов в pre-commit/CI (например, gitleaks).

### 5. Небезопасный удалённый deploy endpoint

`POST /api/deploy` (`server.js:2350`) использует известный запасной ключ при отсутствии `DEPLOY_KEY`, выполняет `git pull` и перезапускает процесс.

Исправление:

- Удалить endpoint из публичного приложения.
- Деплой выполнять через CI/CD или SSH с ключами и сетевыми ограничениями.
- Не иметь запасного ключа в исходном коде; запуск должен прекращаться, если секрет не задан.

## Высокие риски надёжности и поддержки

### Монолитный сервер

`server.js` содержит около 5 136 строк: HTTP-маршруты, торговлю, расчёты, файловое хранение и фоновые интервалы смешаны в одном процессе.

Рекомендуемая декомпозиция:

- `routes/` — HTTP маршруты;
- `services/` — Coinbase, Telegram, market data;
- `trading/` — создание ордеров и риск-лимиты;
- `storage/` — настройки и состояние;
- `jobs/` — фоновые сканеры;
- `middleware/` — auth, validation, rate-limit, error handling.

### Файловое JSON-хранилище

Настройки, история и рабочее состояние читаются/пишутся синхронно в JSON. При параллельных запросах, перезапуске или повреждении файла возможны потери данных.

Исправление:

- Минимум: атомарная запись во временный файл с последующим rename, схема валидации и блокировка записи.
- Предпочтительно: SQLite/PostgreSQL для состояния, истории и журнала операций.

### Нет базовой защиты HTTP-сервера

Не найдены rate limiting, `helmet`, CSRF-защита, ограничения размера JSON-body и централизованная валидация входных данных.

Исправление:

- `helmet`, строгий `express.json({ limit: '...' })`, rate limit;
- схемы Zod/Joi для каждого request body/params;
- единый обработчик ошибок без выдачи внутренних деталей клиенту;
- структурированные логи без токенов, ключей и полных ответов биржи.

## Зависимости и тестирование

### Уязвимые зависимости

`npm audit --omit=dev` на дату аудита: 3 проблемы — 1 high (`path-to-regexp`), 1 moderate (`qs`), 1 low (`body-parser`). Для всех npm сообщает о доступном исправлении.

Исправление:

1. Создать отдельную ветку.
2. Выполнить обновление зависимостей и проверить lockfile.
3. Прогнать ручные и автоматические сценарии торговли в sandbox/paper режиме.

### Нет тестов

У корневого проекта нет команды тестирования. В `cb` команда `test` намеренно завершается ошибкой. При этом `node --check server.js` и `npm run build --prefix cb` прошли.

Минимальный набор тестов:

- авторизация и запрет неавторизованных запросов;
- валидация сумм, пар и лимитов ордера;
- отмена ордера только в разрешённой области;
- ошибки Coinbase и повторные запросы;
- сохранение и восстановление данных;
- отсутствие секретов в API-ответах и логах.

## Приоритетный план исправления

1. Ограничить внешний доступ и отозвать все обнаруженные секреты.
2. Удалить fallback-ключ deploy, закрыть или удалить `/api/deploy`.
3. Добавить аутентификацию, CSRF-защиту и строгий CORS.
4. Перенести Telegram/прочие секреты из JSON и исходников в окружение.
5. Добавить серверные лимиты риска для торговых операций.
6. Обновить зависимости по результату `npm audit`.
7. Покрыть критические пути тестами и затем разделить `server.js` на модули.
